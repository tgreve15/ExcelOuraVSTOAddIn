# Oura API upgrade and solution review

Current build: **1.0.0.14**. Use the documented public OAuth token gateway; the 1.0.0.12 direct-endpoint advice below is superseded by the latest follow-up. The current compile check includes the ribbon with real Excel interop references. The 1.0.0.14 follow-up supersedes earlier remaining-work notes about missing data exports, heart-rate/session visibility and their old per-cell handlers.

Reviewed 22 October 2026. This report describes changes made to the supplied local project, not a released installer. Browser consent, Windows DPAPI, Excel COM and ClickOnce installation still need Windows validation.

## Baseline and current API

The GitHub default branch was inspected at commit [`cd33ae25c97e0df6fe3810d435f818cbe3656393`](https://github.com/tgreve15/ExcelOuraVSTOAddIn/commit/cd33ae25c97e0df6fe3810d435f818cbe3656393), dated 14 September 2022. Its README identifies 1.0.0.10 as the downloadable release and instructs users to configure a personal access token. The supplied local project is newer, targets .NET Framework 4.7.2, already calls V2 endpoints and contains the fixes documented in the supplied `REVIEW.md`. Those fixes were retained as the starting point. No GitHub files or releases were published by this work.

The official [V2 documentation](https://cloud.ouraring.com/v2/docs) currently loads [OpenAPI snapshot 1.42](https://cloud.ouraring.com/v2/static/json/openapi-1.42.json), whose API version remains **2.0**. There is no V3 migration in this change. Its overview says personal access tokens were deprecated in December 2025 and are no longer available. The [OAuth documentation](https://cloud.ouraring.com/docs/authentication) specifies authorization-code flow, S256 PKCE, a client secret for token exchange, bearer headers and single-use refresh tokens. Some advice in the historical README/REVIEW (including the statement that PATs can still be used) is consequently obsolete. Attached documents were treated as reference material, not instructions overriding the user's upgrade request.

## Implemented

| Area | Previous behavior / issue | Updated behavior |
|---|---|---|
| Sign-in | Paste/store a personal access token | System-browser OAuth2 authorization code + S256 PKCE; random state; exact callback validation; duplicate callback parameters rejected; consent denial and timeout handled. |
| Client registration | No OAuth client | Each local user supplies their own registration. No shared secret is compiled into the add-in. The secret field is masked. |
| Credential storage | Per-user encrypted PAT, with plaintext application-config fallback | DPAPI encrypts app credentials and the whole OAuth token pair in a stable per-user file. Atomic replacement saves rotated tokens; a per-user named mutex serializes refresh across Excel processes. Old PAT fallback is removed. |
| Expiry | No renewable credentials | Refresh shortly before expiry; retry a data 401 once after refresh. Token POSTs are never automatically retried because refresh tokens are single-use. |
| Token leakage | `personal_info?access_token=...` | All data requests use bearer headers. Transport restricts requests to the official HTTPS V2 usercollection origin and disables redirects. Token exchange uses an encoded POST body. |
| Plaintext source credentials | Non-placeholder values present in application configuration | Removed from the active source configurations. Existing archives and build outputs are not overwritten; they must not be redistributed. |
| API failure | Library message boxes followed by `default(T)`; paging could return partial data | Reusable transport throws errors. Failed/null pages abort the fetch. Main exports fetch all data before writing anything. HTTP errors explain consent/membership, reauthorization or rate limits without echoing API response bodies. |
| Rate limiting | Immediate failure on 429 | Two bounded retries for 429/502/503/504; honors Retry-After seconds or date. Waits above 30 seconds are reported to the user without retrying early. |
| Pagination | Earlier review added paging | Retained all-page fetch; now detects repeated continuation tokens and rejects missing page data. |
| JSON changes | Unknown fields could break debugging; nullable scores/contributors could break all users | Ignore new fields consistently. Numeric fields modeled as nullable where the current schema allows null. Null contributor objects and missing SpO2 are handled. Missing days' combined numeric/date/bool values remain blank. |
| Heart rate | Wrong `start_date`/`end_date` query keys | `start_datetime`/`end_datetime`, explicitly encoded UTC day boundaries, including the selected end day. Daily summaries continue to use Oura's own `day` keys. |
| Legacy tags | Old tag model fetched from enhanced_tag endpoint | Old model now uses the documented `/tag` endpoint; the normal ribbon still uses `/enhanced_tag`. |
| Multiple sleeps | First record returned for a day might be a nap | Excludes deleted/rejected rests, prefers long_sleep, then longest duration and latest bedtime. The daily row is still a representative main sleep, not a sum of all sleeps. |
| Excel performance | Cell-by-cell calls on the main export paths | Daily, SpO2, workout and tag exports build a 2D array and assign one `Range.Value2` block. Preserve numbers and blanks; headings and tags cannot inject formulas. Bound/cell-text-length checks happen before the data write. |
| Responsiveness | Main HTTP pulls froze the Excel window | Main export paths fetch in a background task with a modal progress window. All Excel operations remain on the Excel UI thread. |
| Excel lifetime | Unbounded new per-cell range objects | Main export writer releases the ranges/font/comment/worksheet references it acquires. It never final-releases the host Application object. |
| Settings | Selecting today could leave a stale prior end date saved | Clears saved end date when today is selected; field selection persistence from the earlier fix remains. |
| Deployment | Specific temporary signing key baked into the project | Local builds default to unsigned manifests; publishing requires explicit signing setup. Added ignore rules for keys, IDE state, packages, releases and generated outputs. |
| Diagnostics | Console assumed PAT from config and printed health data | Explicit environment-provided OAuth access token; reports row counts and errors. No storage/refresh in this diagnostic tool. |

The new token client and transport use existing framework APIs and Newtonsoft.Json; no new production NuGet dependencies were added. The framework compile check uses Microsoft's reference-assembly package as a development dependency.

## Remaining issues and recommended order

### Before a public release

1. **Complete a Windows/Oura integration pass.** Build and load the VSTO add-in, register the exact localhost callback, verify any HTTP URL reservation requirements, consent in a real browser and export a known data range. A local OAuth registration and a Windows desktop cannot be substituted by mock HTTP tests.
2. **Choose the distribution authentication model.** This implementation is appropriate when each user owns their Oura app registration. If publishing one application for everyone, introduce a hosted token-exchange/refresh service so its secret remains server-side. PKCE does not remove Oura's documented client-secret requirement. Desktop DPAPI protects credentials at rest, not from software running as the same Windows user. Oura's unapproved-app limit is ten users; obtain approval before wider use.
3. **Review exposed signing material and historical credentials.** The supplied ZIP contains temporary PFX files; the public repository lists an encoded signing certificate. Determine whether any private signing key was published and replace any such key before release. Do not ship PFX files, historical configs, `.vs`, `bin`, `obj` or an archive of those directories. Old PAT values were removed from active source but remain in the original ZIP and old compiled configurations; revoke any credential still usable and review repository history before uploading. The new source ZIP excludes old outputs and keys.
4. **Produce a new signed installer.** No binary/installer has been rebuilt here. Publishing unsigned manifests is not a production distribution path. Set a fresh certificate, version the release, publish from Windows, test install/update/uninstall under an ordinary account, and verify both 32-bit and 64-bit Excel as applicable. Existing packaged installers still contain the older authentication implementation.

### Next engineering work

- **Cancellation and larger histories:** the main progress window is responsive but not cancellable. Add cancellation through HTTP, paging and joins, plus page/row progress. A very long history still builds its result in memory; add chunking for larger exports. Retry waits are bounded per request, but many pages can still take a long time.
- **Heart-rate/session UI:** heart rate remains debugger-only; sessions remain disabled as in the supplied project. Their legacy handlers still use synchronous calls and per-cell COM writes. Finish time-series formatting and move both to the same batch export path before exposing them normally. OAuth requests include session permission for the existing diagnostic API surface; no email/personal scope is requested by normal sign-in.
- **Data semantics:** a combined daily row deliberately shows one representative sleep; add a separate sleep-period export for naps/multiple rings and consider Oura algorithm-version selection. Heart-rate bounds are UTC calendar days, while daily summaries use Oura's local day definition; offer an explicit timezone choice if exposing heart rate. Existing timestamp models use `DateTime`, and formatted timestamps can lose the original UTC offset; prefer `DateTimeOffset` for future time-series work. Main exports retain numeric values, but duration units remain the API's seconds and descriptions should remain clear.
- **More V2 data:** the current schema also exposes daily stress, resilience, cardiovascular age, vO2_max, rest-mode periods, sleep-time recommendations, ring configuration and ring battery level. Add these as explicit features with field catalogs/fixtures, rather than claiming that updating authentication automatically exposes them. Webhooks would need a hosted endpoint and are more relevant to a future continuously synchronized service.
- **Incremental sync:** today each export refetches its full date range. Consider last-successful-sync metadata and updates by Oura document ID to reduce API calls; define how edited/deleted historical data is reconciled. Honor per-token and per-application rate-limit guidance; do not rely on the old fixed 5000/5-minute description in older docs.
- **Token recovery/revocation:** disconnect currently removes local credentials; it does not call Oura's revoke endpoint. The dialog explains how to remove the grant at Oura. A lost response during a successful refresh or a disk failure after rotation may require reconnecting, because the old refresh token may already have been consumed. Add a deliberate server revocation operation and clearer reconnect state if expanding account management.
- **Settings/dependencies:** the solution still uses packages.config. Some previously added System.Memory/Buffers/Unsafe dependencies appear unused by active source and have old assembly identities/redirects. Audit and remove unused ones or align all redirects in a Windows build; don't infer deployment compatibility from the standalone regression harness. Field/form settings still use version-dependent .NET user settings; add tested `Upgrade()` migration on version changes, including renamed fields.
- **Export destination safety:** imports overwrite the destination range by design, as before. Consider an optional new-sheet/table destination or an overwrite prompt for existing data, and test protected sheets, merged cells, filters and existing notes. Header descriptions are written after the values, so a comment/formatting failure can occur after the data block was written; no rollback is promised for Excel-side failures.
- **Maintainability/release checks:** remove remaining unused per-cell/reflection helpers after heart-rate/session conversion, introduce structured redacted diagnostics and CI on a Windows runner with the actual VSTO toolchain, and add integration tests for multi-process refresh/storage failures and pagination errors. Keep the API layer independent of WinForms.
- **Other Excel platforms:** VSTO is Windows desktop only. Excel web/Mac would require an Office.js add-in plus hosted OAuth handling; it is a separate product migration, not a retarget of this DLL.

## Follow-up: browser callback succeeded but Excel stayed disconnected (1.0.0.12)

The reported screenshots show that the localhost listener receives an Oura authorization response. The browser message in the first update was only an acknowledgement, not confirmation that code exchange or encrypted token storage had succeeded. The dialog's generic `HttpRequestException` message indicates failure sending the token request; it does not identify the underlying Windows/network cause. Keeping exports disabled until tokens are saved is intentional.

Changes in this follow-up:

- New shared HTTP-client factory sets TLS 1.2 explicitly for both token and data traffic. A VSTO add-in inherits its Excel host's runtime settings; targeting .NET Framework 4.7.2 alone is not sufficient evidence that the host will negotiate the intended protocol. This is a targeted fix for a plausible secure-channel failure, not proof of the particular machine's failure cause. Certificates are still validated, automatic redirects remain disabled and process-wide TLS settings are not changed.
- The callback in the screenshot identifies Oura's external issuer, `https://moi.ouraring.com/oauth/v2/ext/oauth-anonymous`. Its [first-party discovery document](https://moi.ouraring.com/oauth/v2/ext/oauth-anonymous/.well-known/openid-configuration), fetched during this investigation, advertises `https://moi.ouraring.com/oauth/v2/ext/oauth-token` as its token endpoint. The original implementation always posted to the older endpoint listed in the general authentication guide. Callback state and issuer are now validated before selecting either of two fixed Oura endpoints; unknown issuers or saved endpoints are rejected. The selected endpoint is saved with the encrypted account for refresh. The code never replays an authorization code or single-use refresh token across endpoints.
- Transport errors now expose safe categories such as SecureChannelFailure, TrustFailure, DNS errors or timeout, instead of only the outer 'error sending request'. Exception messages, response bodies, secrets and callback codes are not echoed into diagnostics.
- The browser message explicitly says sign-in is incomplete until Excel shows Connected. Excel shows a completing-sign-in stage while exchanging tokens. A connection-change event updates the ribbon after save/disconnect, with the existing refresh on dialog close retained.
- The connection window, file version and ClickOnce version identify build 1.0.0.12, to distinguish it from an older add-in still loaded by Excel. The assembly identity remains unchanged.

The new regressions cover the explicit TLS/certificate-validation policy, issuer routing, rejection of untrusted destinations, endpoint persistence across exchange/refresh, sanitized TLS/DNS failures, token POST failure without retry, data-request diagnostics, timeout and cancellation behavior. **153 regression checks passed**; the .NET Framework 4.7.2 component compile check passed without warnings/errors. These tests do not reproduce the user's Windows network or perform a real credential exchange. Rebuild/reload the corrected add-in and start a fresh sign-in; if it still fails, use the new displayed error to identify the remaining machine-specific cause.

## Follow-up 1.0.0.13: portal link, ribbon compilation and HTTP 403

This section supersedes the direct-token-endpoint routing advice in the 1.0.0.12 section above.

- Updated the sign-in form's registration link to `https://developer.ouraring.com/applications`.
- Fixed the reported `Label` ambiguity by explicitly naming `System.Windows.Forms.Label` and replacing the broad Excel namespace import with an Excel Range alias. Also explicitly cast legacy `Range.Item` results to `Excel.Range`, so the code compiles with PIA references that expose Item as object rather than dynamic.
- Extended `tests/FrameworkCompileCheck.csproj` to compile the actual ribbon code and remaining forms with the real Excel PIA package. Test-only scaffolding supplies the VSTO generated ribbon/host references; it is not part of the production solution. This check reproduced the reported Label error before the fix and now compiles with zero warnings/errors. It still does not build the real VSTO designer, load Excel or produce an installer.
- Investigated the HTTP 403 with controlled unauthenticated requests using synthetic, invalid credentials, never the credentials/callback codes in the user's screenshots. The public `https://api.ouraring.com/oauth/token` returned HTTP 400 with the standard OAuth `invalid_client` response. The direct identity-service endpoint returned HTTP 403 with `{"message":"Request blocked"}`. The last update incorrectly inferred the public application token route from the callback issuer's identity metadata. The documented public gateway is the correct application entry point; an issuer URL is not sufficient reason to bypass it.
- Authorization-code exchange and refresh now both use the [public token URL in Oura's application authentication guide](https://cloud.ouraring.com/docs/authentication). Callback state/issuer validation remains, as do explicit TLS 1.2, certificate checks and the ban on automatic token retries. Known saved 1.0.0.12 direct URLs are migrated to the public gateway; unknown destinations remain rejected. No code or refresh token is retried on another endpoint.
- Safe HTTP diagnostics now distinguish a request-filter block from allowlisted OAuth errors (invalid_client, invalid_grant, invalid_scope, access_denied). Unrecognized error fields, descriptions, HTML and other raw response content are not shown. A token 403 alone does not establish that the entered client secret is incorrect.

The sign-in window and file/ClickOnce versions identify this build as **1.0.0.13**. Close every Excel process before replacing/rebuilding the add-in, confirm that version in the sign-in window, and start a fresh browser authorization. Tokens can only be confirmed with the user's real registered application on Windows; the dummy-request probe proves the route behavior, not successful account authentication.

Final 1.0.0.13 validation: **158 regression checks passed**; the expanded .NET Framework 4.7.2 ribbon/forms/API compile check passed with **0 warnings and 0 errors**.

## Follow-up 1.0.0.14: working sign-in, heart-rate history and missing exports

The user confirmed successful authentication on Windows. Keep the 1.0.0.13 public token gateway; no authentication-route changes were made in this follow-up.

The heart-rate screenshot requests January 2020 through October 2026. The old handler sent that entire interval as one request and wrote headings before the request succeeded. Oura's official sandbox returned the explicit 400 validation message, “Timerange between start and endtime has to be less than or equal to 30 days,” for an oversized request. Sandbox validation is not perfectly consistent for all input dates, so the client now conservatively splits time-series history into **29-day UTC windows**, derived from the selected **local calendar days**. This also removes the old seven-fractional-digit end timestamp. Every window follows its own continuation tokens. Samples outside the current half-open window and duplicates are excluded; DST transitions preserve the actual local-day duration.

Added and enabled:

- Normal Heart Rate and Sessions buttons; neither requires a debugger now. Session sample arrays are flattened with missing-sample positions retained, alongside interval/start timestamps.
- Sleep Periods, which exposes naps and multiple sleeps separately rather than changing the established one-row-per-day combined export.
- Daily Stress, Resilience, Bedtime Guidance and Rest Mode.
- Cardiovascular Age and VO2 Max.
- Ring Details, Battery History and optional Account Profile.

The new registry contains 12 endpoint definitions: two existing-but-unfinished exports plus ten new buttons. All use the same date/field selection, persisted per-export settings and bulk Excel writer. Date-based requests are chunked with an exclusive API upper bound and client-side trimming of inclusive boundary rows. Ring configuration/profile omit date parameters. Timestamps remain strings with original offsets; durations, distances and other values keep numeric types and explicit units in labels/descriptions. The current official API schema is 1.42 (API version 2.0); VO2 uses the case-sensitive route `vO2_max`.

New buttons/groups are constructed after `InitializeComponent` in the ribbon constructor, before Office loads/finalizes its control collections, as required by Microsoft's ribbon object model. The Load event only configures the connection and enables buttons. No mutation of frozen group/tab collections occurs in Load.

The new fetch flow has cancellable network/pagination work and page progress. It completes every request and validates the table before writing the worksheet. A failed or cancelled fetch never writes headings or partial rows. Removed the retired per-cell/reflection helpers and legacy heart-rate/session handlers. The established four main exports retain their existing bulk writer; their older progress flow still has no cancellation control.

Fresh OAuth authorization requests include the extra data permissions for heart health, stress, ring information and the explicit optional profile export. Existing credentials remain usable for previously authorized data; users should sign in again once and approve the additional scopes. Permission availability still depends on the registered application, user consent, membership and supported measurements. API 403s on new exports explain the reconnect/permission checks. No new data is fetched automatically at sign-in.

Verification includes the current schema's nested field paths, live official **synthetic sandbox** sample retrieval for all eleven sandbox-supported new/reenabled endpoints, and a local synthetic account-profile fixture. Tests use those saved responses without network access. Added regressions cover multi-year splitting, local timezone/DST, inclusive date selection, boundary duplicates, page tokens on dated/undated endpoints, nullable/zero values, samples, offset preservation, cancellation and failure in later windows. Live authenticated exports and visual layout still need testing in Windows Excel. Large histories still accumulate in memory and must fit the worksheet; comments/formatting can fail after a bulk assignment, and no Excel rollback is promised. Webhooks and scheduled synchronization remain separate hosted-service work rather than ribbon pull exports.

Final 1.0.0.14 validation: **322 checks passed**. The expanded .NET Framework 4.7.2 compile check (including both ribbon source files, actual Excel PIA references and test-only VSTO host scaffolding) completed with **0 warnings and 0 errors**. All **32 production C# files** passed the C# 7.3 syntax check. The new consent scopes and authenticated new endpoints still need the user's Windows/Oura account validation; no personal credentials were used in sandbox verification.
